<h2 id="requirements">1. Requirements (~5 minutes)</h2>

The interview prompt is usually short:

> “Design a meeting-room scheduler.”

We all understand meetings and rooms, but that familiarity can hide unanswered questions. Does the caller choose a room? Does a meeting ending at 10:00 conflict with one starting at 10:00? Are attendee calendars included? Can anybody cancel another person's meeting?

Do not begin with a `Room` class. First turn the vague prompt into actions whose results both you and the interviewer can predict.

Read the arrows from left to right. The **Organizer** submits a request to **MeetingScheduler**. The scheduler asks **RoomSelectionStrategy** to compare rooms. The strategy calls each **Room**, and Room uses its capacity, equipment, ordered meetings, and the requested **TimeSlot**. The chosen Room reserves the slot, which allows the scheduler to create a **Meeting**. If no Room qualifies, the same path returns a rejection and no Meeting is created.

The boundary matters: the strategy may *choose* a Room, but it cannot write into that Room's schedule. `Room.reserve` repeats the availability check and owns the state change.

<h2 id="class-design">3. Class design (10–15 minutes)</h2>

Move from the entities into methods using the same chain:

> requirement → responsible object → state it remembers → method that changes or reads that state

Start at `MeetingScheduler.schedule` because that is the caller-visible action. Then follow its questions downward: which rooms qualify, and how does one Room know that its time is free?

<ClassDesignExplorer topic={meetingRoomClassDesign} />

The explorer shows that Room—not MeetingScheduler—owns interval and schedule state. The next sections explain the half-open interval and TreeMap neighbour rules that make Room's invariant efficient.

### Scheduling concept: half-open intervals

Write a time slot as `[start, end)`. The square bracket means the start belongs to the meeting. The round bracket means the end does not.

For a meeting `[09:00, 10:00)`, the occupied times include 09:00 and 09:59, but not 10:00. Therefore `[10:00, 10:30)` can begin immediately.

Two slots overlap only when both statements are true:

```text
first.start < second.end
second.start < first.end
```

Why use two comparisons? Consider `[09:00, 10:00)` and `[10:00, 10:30)`:

- `09:00 < 10:30` is true.
- `10:00 < 10:00` is false.
- Both are not true, so the slots do not overlap.

Using `<=` would wrongly reject every back-to-back meeting. That one character is a common interview bug.

### Why an ordered schedule needs only two neighbour checks

`Room` stores accepted meetings in a `TreeMap` keyed by start time. A TreeMap keeps keys sorted and can quickly find the closest entry before or after a requested start.

Suppose the schedule is:

```text
[08:30, 09:00)   [09:00, 10:00)   [10:30, 11:00)
```

For a new `[10:00, 10:30)` slot:

1. `floorEntry(10:00)` returns `[09:00, 10:00)`, the closest meeting starting at or before 10:00.
2. It touches but does not overlap.
3. `ceilingEntry(10:00)` returns `[10:30, 11:00)`, the closest meeting starting at or after 10:00.
4. It also touches but does not overlap.
5. No more distant meeting can overlap without crossing one of those neighbours.

This last step depends on an **invariant**: a promise the object always keeps. Room never stores overlapping meetings. Because existing entries do not overlap, checking the predecessor and successor is sufficient.

If one room has `M` meetings, each neighbour lookup costs `O(log M)`. Checking `R` rooms costs `O(R log M)` in the simplified worst case, and inserting the accepted meeting costs another `O(log M)`. Total space is `O(R + N)` for rooms and all `N` accepted meetings.

<Insight title="The data structure is useful because Room protects its invariant" tone="warning">
  A TreeMap alone does not prevent overlap. Correctness comes from allowing schedule changes only through `Room.reserve`, which checks the neighbours before inserting. Exposing the map would let callers break the assumption that makes the fast check valid.
</Insight>

### Understand deterministic room selection

The strategy filters in this order:

1. Enough capacity.
2. Every required equipment item.
3. No overlapping meeting.
4. Among survivors, lower capacity wins.
5. If capacity ties, lower room ID wins.

For four people needing a projector, a free 4-seat room beats a free 10-seat room. This preserves the large room for a later request that may actually need it. The ID comparison is not a business optimization; it makes equal cases predictable.

`RoomSelectionStrategy` owns this comparison and nothing else. It may call `Room.canHost`, but it cannot reserve the winner, allocate an ID, or update scheduler indexes. That read-only boundary lets a future policy change without moving the Room invariant or cancellation workflow.

### Decide whether patterns help

<PatternDecision name="Strategy for room selection" useIt={true}>
  The requirement explicitly says selection may change. `RoomSelectionStrategy.select(rooms, request)` is the boundary. `SmallestSuitableRoomStrategy` implements today's capacity-and-ID rule. A future nearest-floor strategy can replace it without changing interval checks, meeting creation, or cancellation.
</PatternDecision>

<PatternDecision name="Observer for invitations" useIt={false}>
  The first version sends no invitations or notifications. There are no listeners to notify. Add Observer-like event handling only when a confirmed requirement introduces several reactions to a successful schedule or cancellation.
</PatternDecision>

<PatternDecision name="Singleton MeetingScheduler" useIt={false}>
  A global instance does not prevent conflicts across servers and makes tests share mutable state. Normal construction keeps rooms and strategy explicit.
</PatternDecision>

<PatternDecision name="Factory for Meeting" useIt={false}>
  Meeting construction is one visible record constructor after room selection. A factory would hide simple values without solving a creation rule. Add one only if creation later needs several meeting types or external configuration.

### Connect the classes and review the final blueprint

MeetingScheduler has Rooms and one RoomSelectionStrategy. Each Room owns its ordered Meetings, and every Meeting contains one TimeSlot. These composition relationships match the responsibilities; none of the classes is a specialized form of another.

- **Immutability:** requests, time slots, and accepted meetings cannot change behind the schedule.
- **Encapsulation:** Room never exposes its mutable TreeMap and validates every insertion.
- **Single responsibility:** TimeSlot owns overlap, Room owns one schedule, Strategy selects, and Scheduler coordinates.
- **Open/closed design:** a new room policy implements the Strategy boundary without changing interval correctness.
- **Validation before mutation:** failed scheduling and cancellation leave schedules, indexes, and the next accepted ID unchanged.

### Code concepts to understand

<ConceptDropdown title="Half-open TimeSlot" summary="One value object keeps boundary behavior identical everywhere." defaultOpen={true}>
  `TimeSlot.overlaps` uses two strict `isBefore` comparisons. Strict comparisons make equal end and start times non-overlapping. The constructor rejects an end that is equal to or before the start, so every created TimeSlot is meaningful.
</ConceptDropdown>

<ConceptDropdown title="TreeMap predecessor and successor" summary="An ordered, non-overlapping schedule avoids scanning every meeting.">
  `floorEntry(request.start)` finds the closest existing start at or before the request. `ceilingEntry(request.start)` finds the closest at or after it. Room checks both with the same `TimeSlot.overlaps` method. This is correct because `reserve` never permits existing meetings to overlap.
</ConceptDropdown>

<ConceptDropdown title="Immutable request and result records" summary="Requested values and accepted facts cannot be edited behind the scheduler's back.">
  `MeetingRequest`, `TimeSlot`, and `Meeting` are records. Their constructors copy equipment sets, so a caller cannot modify the original Set after construction and silently change the request or meeting.
</ConceptDropdown>

<ConceptDropdown title="Validation before state change" summary="A rejection leaves every room exactly as it was.">
  Strategy checks all qualifications before a Meeting exists. `Room.reserve` checks again before `TreeMap.put`. MeetingScheduler adds the global index only after reserve succeeds. Cancellation checks existence and ownership before removing from either place.
</ConceptDropdown>

<ConceptDropdown title="Strategy call flow" summary="The pattern isolates only the rule that actually varies.">
  MeetingScheduler calls `strategy.select(rooms, request)`. The strategy does not inspect private maps; it calls `room.canHost(request)`. The returned Room still performs `reserve`. Selection and ownership of schedule state remain separate.
</ConceptDropdown>

### Let Room protect the ordered schedule

Read `isAvailable` before `reserve`. The first method explains the neighbour algorithm; the second shows how the state change remains behind the same validation boundary.

<JavaFile name="Room.java" purpose="Owns suitability facts, ordered meetings, overlap checks, reservation, and removal.">
{`import java.time.LocalDateTime;
import java.util.List;
import java.util.Map;
import java.util.Set;
import java.util.TreeMap;

public final class Room {
    private final String id;
    private final String name;
    private final int capacity;
    private final Set<Equipment> equipment;
    private final TreeMap<LocalDateTime, Meeting> schedule = new TreeMap<>();

    public Room(String id, String name, int capacity, Set<Equipment> equipment) {
        if (id == null || id.isBlank() || name == null || name.isBlank()) {
            throw new IllegalArgumentException("Room id and name are required");
        }
        if (capacity <= 0 || equipment == null) {
            throw new IllegalArgumentException("Valid capacity and equipment are required");
        }
        this.id = id;
        this.name = name;
        this.capacity = capacity;
        this.equipment = Set.copyOf(equipment);
    }

    public String id() {
        return id;
    }

    public String name() {
        return name;
    }

    public int capacity() {
        return capacity;
    }

    public Set<Equipment> equipment() {
        return equipment;
    }

    public boolean canHost(MeetingRequest request) {
        return capacity >= request.attendeeCount()
                && equipment.containsAll(request.requiredEquipment())
                && isAvailable(request.slot());
    }

    public boolean isAvailable(TimeSlot requested) {
        Map.Entry<LocalDateTime, Meeting> previous =
                schedule.floorEntry(requested.start());
        if (previous != null && previous.getValue().slot().overlaps(requested)) {
            return false;
        }

        Map.Entry<LocalDateTime, Meeting> next =
                schedule.ceilingEntry(requested.start());
        return next == null || !next.getValue().slot().overlaps(requested);
    }

    public boolean reserve(Meeting meeting) {
        if (!id.equals(meeting.roomId())
                || capacity < meeting.attendeeCount()
                || !equipment.containsAll(meeting.requiredEquipment())
                || !isAvailable(meeting.slot())) {
            return false;
        }
        schedule.put(meeting.slot().start(), meeting);
        return true;
    }

    public boolean remove(Meeting meeting) {
        if (meeting == null || !id.equals(meeting.roomId())) {
            return false;
        }
        return schedule.remove(meeting.slot().start(), meeting);
    }

    public List<Meeting> meetings() {
        return List.copyOf(schedule.values());
    }
}`}
</JavaFile>

<JavaFile name="MeetingScheduler.java" purpose="Coordinates room selection, accepted IDs, meeting lookup, and owner-only cancellation.">
{`import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public final class MeetingScheduler {
    private final List<Room> rooms;
    private final Map<String, Room> roomsById;
    private final Map<String, Meeting> meetingsById = new LinkedHashMap<>();
    private final RoomSelectionStrategy strategy;
    private int nextMeetingNumber = 1;

    public MeetingScheduler(
            List<Room> rooms,
            RoomSelectionStrategy strategy
    ) {
        if (rooms == null || rooms.isEmpty() || strategy == null) {
            throw new IllegalArgumentException("Rooms and strategy are required");
        }
        this.rooms = List.copyOf(rooms);
        this.strategy = strategy;
        this.roomsById = new LinkedHashMap<>();
        for (Room room : rooms) {
            if (roomsById.putIfAbsent(room.id(), room) != null) {
                throw new IllegalArgumentException("Duplicate room: " + room.id());
            }
        }
    }

    public ScheduleResult schedule(MeetingRequest request) {
        if (request == null) {
            throw new IllegalArgumentException("Request is required");
        }

        Optional<Room> selected = strategy.select(rooms, request);
        if (selected.isEmpty()) {
            return ScheduleResult.rejected();
        }

        Room room = selected.get();
        String meetingId = "M" + nextMeetingNumber;
        Meeting meeting = new Meeting(
                meetingId,
                request.title(),
                request.organizerId(),
                room.id(),
                request.slot(),
                request.attendeeCount(),
                request.requiredEquipment()
        );

        if (!room.reserve(meeting)) {
            return ScheduleResult.rejected();
        }
        nextMeetingNumber++;
        meetingsById.put(meeting.id(), meeting);
        return ScheduleResult.accepted(meeting);
    }

    public CancellationStatus cancel(
            String meetingId,
            String organizerId
    ) {
        Meeting meeting = meetingsById.get(meetingId);
        if (meeting == null) {
            return CancellationStatus.MEETING_NOT_FOUND;
        }
        if (!meeting.organizerId().equals(organizerId)) {
            return CancellationStatus.NOT_ORGANIZER;
        }

        Room room = roomsById.get(meeting.roomId());
        if (!room.remove(meeting)) {
            throw new IllegalStateException("Meeting index and room disagree");
        }
        meetingsById.remove(meetingId);
        return CancellationStatus.CANCELED;
    }

    public List<Meeting> meetingsForRoom(String roomId) {
        Room room = roomsById.get(roomId);
        return room == null ? List.of() : room.meetings();
    }
}`}

<h2 id="extensions">5. Extensions (~5 minutes)</h2>

Each follow-up begins by changing one requirement, then changing the smallest responsible boundary.

### Add room setup and cleanup buffers

If every meeting needs ten minutes of preparation, the requested interval used for conflict checking expands before selection. `TimeSlot` can expose a buffered copy, while the Meeting still stores the visible start and end. Clarify whether back-to-back meetings are still allowed before changing the formula.

### Add recurring meetings

A recurring request is not one Meeting. Add a recurrence rule that expands into a finite set of TimeSlots for a stated date range. Scheduling must validate **all** occurrences before reserving any, or roll back earlier inserts if a later date fails. Do not store “forever” recurrence without a boundary.

### Add attendee calendars

The new requirement creates an Attendee calendar owner. Room availability and person availability become separate checks. MeetingScheduler coordinates both, but each calendar should still own its own overlap rule. Invitations and response states enter only if the interviewer asks for them.

### Handle simultaneous requests

The current check-then-reserve flow assumes sequential calls. In one Java process, `Room.reserve` could protect its neighbour check and insert with a lock. Across application servers, use a shared database transaction or constraint. A Strategy result alone is never a distributed reservation guarantee.

### Search a large organization efficiently

With thousands of rooms, first index fixed properties such as building, capacity, and equipment. The scheduler retrieves a smaller candidate set, then checks each candidate's ordered schedule. Keep the exact capacity and room-ID tie-breakers so the result remains deterministic.
