<h2 id="requirements">1. Requirements (~5 minutes)</h2>

The interview prompt is often only:

> “Design Splitwise.”

That sentence does not yet tell us what to build. Does one person pay the complete bill? Are unequal shares allowed? Should `33.33% + 33.33% + 33.34%` be supported? Does “simplify” change old expenses? What happens when an invalid split is submitted?

Do not begin by drawing `User`, `Expense`, and `Group`. First make the money rules exact enough that two interviewers would calculate the same answer.

<h2 id="class-design">3. Class design (10–15 minutes)</h2>

Move from requirements to code with the same chain:

> requirement → responsible object → state it remembers → method that changes or reads that state

Start with `ExpenseService.recordExpense` because it is the caller-visible action. Then follow its questions downward: are the users valid, which strategy calculates shares, and how does BalanceSheet apply them?

<ClassDesignExplorer topic={splitwiseClassDesign} />

The explorer separates ExpenseService orchestration from BalanceSheet mutation. The following lessons explain the exact-cent arithmetic and netting rules that make the ledger correct.

### Money concept: cents, remainders, and exact totals

The practical problem is a $10.00 bill shared by three users. Decimal division says `$3.333...`, but nobody can pay a fraction of one cent.

If we round every share to `$3.33`, the stored shares total `$9.99`. One cent disappears. If this happens across many bills, the balance sheet no longer matches the expense history.

The core rule is **conservation of money**: the sum of calculated shares must equal the original total exactly.

For an equal split, integer arithmetic makes the rule visible:

```text
total = 1000 cents, people = 3
base = 1000 / 3 = 333 cents
remainder = 1000 % 3 = 1 cent
shares in sorted ID order = 334, 333, 333 cents
```

For percentages, each user first receives the whole-cent floor. Leftover cents go to the users with the largest fractional remainders; equal remainders use user ID. This is called the **largest remainder method**. It is deterministic and keeps the total exact.

Calculating `N` shares costs `O(N log N)` because the implementation sorts participant IDs or fractional remainders. A hash-map approach could reduce some work, but deterministic rounding would still need an ordering.

### Balance concept: net opposite debts immediately

Suppose Ava owes Ben `$30`, then a new expense makes Ben owe Ava `$50`. Storing both arrows is valid history but a poor current balance.

BalanceSheet converts both updates to one signed value on the same sorted pair:

```text
AVA → BEN $30  becomes +3000 on pair (AVA, BEN)
BEN → AVA $50  becomes -5000 on pair (AVA, BEN)
combined value = -2000
meaning: BEN owes AVA $20
```

This creates an invariant—something that must remain true after every operation: for one user pair, at most one debt direction exists. `addDebt` owns this rule because it owns the signed pair map.

Adding one debt is expected `O(1)` with the hash map. Returning balances costs `O(P log P)` to sort `P` non-zero pairs for predictable display.

### Simplification concept: preserve net position, change the route

After the illustrated dinner and taxi, pairwise history says:

- Ben owes Ava `$40`.
- Cara owes Ava `$40`.
- Cara owes Ben `$30`.

For each person, add money they should receive and subtract money they owe. Ava's net position is `+$80`, Ben's is `-$10`, and Cara's is `-$70`. A positive number means the group owes that user; a negative number means that user owes the group.

DebtSimplifier keeps two ordered groups: debtors and creditors. It repeatedly matches the largest remaining debtor with the largest remaining creditor and transfers the smaller remaining amount. The result is Cara → Ava `$70` and Ben → Ava `$10`.

With `U` users and `P` pairwise debts, building net positions costs `O(P)`. Priority queues make matching cost `O(U log U)`, and the result uses at most `U - 1` transfers. This greedy result is deterministic, but it is not promised to be the mathematically smallest possible number of payments for every input. That harder optimization is deliberately out of scope.

<PatternDecision name="Strategy for split calculation" useIt={true}>

<PatternDecision name="Observer for notifications" useIt={false}>

<PatternDecision name="Singleton ExpenseService" useIt={false}>

### Code concepts to understand

<ConceptDropdown title="Money as integer cents" summary="Whole cents avoid floating-point surprises and make exact totals testable." defaultOpen={true}>
  `Money` stores a non-negative `long`. EqualSplitStrategy uses quotient and remainder. PercentageSplitStrategy uses basis points and integer numerators. No code stores `double` amounts, so `$0.10 + $0.20` cannot become an imprecise binary fraction.
</ConceptDropdown>

<ConceptDropdown title="Strategy call flow" summary="The pattern isolates only the share calculation that actually varies.">
  ExpenseService selects a strategy from an `EnumMap`, then calls `calculate`. The returned share map has one common shape. The strategies never edit balances; BalanceSheet does not know which split type produced an amount.
</ConceptDropdown>

<ConceptDropdown title="Signed canonical pair" summary="One sorted key stores either direction of debt between two users.">
  `PairKey.of` always puts the lower user ID first. `addDebt` chooses a positive or negative delta from the actual debtor direction. Adding the delta automatically cancels opposite debt, and a zero result removes the map entry.
</ConceptDropdown>

<ConceptDropdown title="Validation before mutation" summary="An invalid split cannot create an ID, history entry, or partial debt.">
  ExpenseService checks identities and asks Strategy for the complete share map first. It catches strategy input errors and returns `INVALID_SPLIT`. Only then does it increment the ID, append Expense, and call BalanceSheet.
</ConceptDropdown>

<ConceptDropdown title="Priority queues in simplification" summary="The largest remaining debtor and creditor can be selected repeatedly without re-sorting every time.">
  DebtSimplifier turns pairwise debts into net positions, adds non-zero users to two priority queues, and matches the queue heads. Each match clears at least one user, so there are at most `U - 1` suggestions.
</ConceptDropdown>

<ConceptDropdown title="Why simplified debts are not stored" summary="A suggestion is a view of current obligations, not the source of truth.">
  Expense history explains why balances exist. Pairwise BalanceSheet explains which real user pairs owe money. Replacing those with suggestions would discard that relationship. The simplifier therefore returns new Debt values and never mutates its input.
</ConceptDropdown>

### Implement the three split rules

The interface accepts one generic values map: exact strategies read cents; percentage strategies read basis points; equal strategy needs no values. ExpenseService hides this input detail from BalanceSheet.

<JavaFile name="SplitStrategy.java" purpose="Defines the common boundary for every share calculation.">
{`import java.util.List;
import java.util.Map;

public interface SplitStrategy {
    Map<String, Money> calculate(
            Money total,
            List<String> participantIds,
            Map<String, Long> values

}`}
</JavaFile>

<JavaFile name="EqualSplitStrategy.java" purpose="Divides cents equally and assigns leftover cents by sorted user ID.">
{`import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public final class EqualSplitStrategy implements SplitStrategy {
    @Override
    public Map<String, Money> calculate(
            Money total,
            List<String> participantIds,
            Map<String, Long> ignored
    ) {
        List<String> ordered = participantIds.stream().sorted().toList();
        if (ordered.isEmpty()) {
            throw new IllegalArgumentException("Participants are required");
        }

        long base = total.cents() / ordered.size();
        long remainder = total.cents() % ordered.size();
        Map<String, Money> shares = new LinkedHashMap<>();
        for (int index = 0; index < ordered.size(); index++) {
            long cents = base + (index < remainder ? 1 : 0);
            if (cents == 0) {
                throw new IllegalArgumentException("Every share must be positive");
            }
            shares.put(ordered.get(index), Money.ofCents(cents));
        }
        return Map.copyOf(shares);
    }
}`}
</JavaFile>

<JavaFile name="ExactSplitStrategy.java" purpose="Accepts positive cent amounts only when they exactly total the bill.">
{`import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

public final class ExactSplitStrategy implements SplitStrategy {
    @Override
    public Map<String, Money> calculate(
            Money total,
            List<String> participantIds,
            Map<String, Long> values
    ) {
        Set<String> expected = Set.copyOf(participantIds);
        if (expected.isEmpty() || expected.size() != participantIds.size()
                || values == null || !values.keySet().equals(expected)) {
            throw new IllegalArgumentException("One exact value per participant is required");
        }

        long sum = 0;
        Map<String, Money> shares = new LinkedHashMap<>();
        for (String id : expected.stream().sorted().toList()) {
            long cents = values.get(id);
            if (cents <= 0) {
                throw new IllegalArgumentException("Exact shares must be positive");
            }
            sum = Math.addExact(sum, cents);
            shares.put(id, Money.ofCents(cents));
        }
        if (sum != total.cents()) {
            throw new IllegalArgumentException("Exact shares must equal total");
        }
        return Map.copyOf(shares);
    }
}`}
</JavaFile>

<JavaFile name="PercentageSplitStrategy.java" purpose="Uses basis points and the largest remainders to preserve every cent.">
{`import java.util.ArrayList;
import java.util.Comparator;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

public final class PercentageSplitStrategy implements SplitStrategy {
    private record Fraction(String userId, long remainder) {}

    @Override
    public Map<String, Money> calculate(
            Money total,
            List<String> participantIds,
            Map<String, Long> basisPointsByUser
    ) {
        Set<String> expected = Set.copyOf(participantIds);
        if (expected.isEmpty() || expected.size() != participantIds.size()
                || basisPointsByUser == null
                || !basisPointsByUser.keySet().equals(expected)) {
            throw new IllegalArgumentException("One percentage per participant is required");
        }

        long basisPointSum = 0;
        long allocated = 0;
        Map<String, Long> centsByUser = new LinkedHashMap<>();
        List<Fraction> fractions = new ArrayList<>();

        for (String id : expected.stream().sorted().toList()) {
            long basisPoints = basisPointsByUser.get(id);
            if (basisPoints <= 0) {
                throw new IllegalArgumentException("Percentages must be positive");
            }
            basisPointSum = Math.addExact(basisPointSum, basisPoints);
            long numerator = Math.multiplyExact(total.cents(), basisPoints);
            long cents = numerator / 10_000;
            centsByUser.put(id, cents);
            allocated += cents;
            fractions.add(new Fraction(id, numerator % 10_000));
        }
        if (basisPointSum != 10_000) {
            throw new IllegalArgumentException("Percentages must total 100%");
        }

        fractions.sort(Comparator.comparingLong(Fraction::remainder)
                .reversed().thenComparing(Fraction::userId));
        long leftover = total.cents() - allocated;
        for (int index = 0; index < leftover; index++) {
            String id = fractions.get(index).userId();
            centsByUser.put(id, centsByUser.get(id) + 1);
        }

        Map<String, Money> shares = new LinkedHashMap<>();
        for (String id : expected.stream().sorted().toList()) {
            long cents = centsByUser.get(id);
            if (cents == 0) {
                throw new IllegalArgumentException("Every share must be positive");
            }
            shares.put(id, Money.ofCents(cents));
        }
        return Map.copyOf(shares);
    }
}`}
</JavaFile>

### Let BalanceSheet protect pairwise debt

Read `addDebt` first. It turns a real direction into a signed delta on the canonical pair. Then read `balances`, which translates the private representation back into readable Debt values.

<JavaFile name="BalanceSheet.java" purpose="Owns canonical pairwise debt, opposite-direction netting, and direct settlement.">
{`import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public final class BalanceSheet {
    private record PairKey(String first, String second) {
        static PairKey of(String left, String right) {
            return left.compareTo(right) < 0
                    ? new PairKey(left, right)
                    : new PairKey(right, left);
        }
    }

    private final Map<PairKey, Long> signedByPair = new HashMap<>();

    public void addDebt(String debtorId, String creditorId, Money amount) {
        if (debtorId == null || creditorId == null || amount == null
                || debtorId.equals(creditorId) || amount.cents() == 0) {
            return;
        }
        PairKey key = PairKey.of(debtorId, creditorId);
        long delta = debtorId.equals(key.first())
                ? amount.cents()
                : -amount.cents();
        long combined = Math.addExact(signedByPair.getOrDefault(key, 0L), delta);
        if (combined == 0) {
            signedByPair.remove(key);
        } else {
            signedByPair.put(key, combined);
        }
    }

    public SettlementStatus settle(
            String debtorId,
            String creditorId,
            Money amount
    ) {
        if (amount == null || amount.cents() == 0
                || debtorId == null || creditorId == null
                || debtorId.equals(creditorId)) {
            return SettlementStatus.INVALID_AMOUNT;
        }
        Debt current = balances().stream()
                .filter(debt -> debt.debtorId().equals(debtorId)
                        && debt.creditorId().equals(creditorId))
                .findFirst()
                .orElse(null);
        if (current == null) {
            return SettlementStatus.NO_MATCHING_DEBT;
        }
        if (amount.cents() > current.amount().cents()) {
            return SettlementStatus.AMOUNT_EXCEEDS_DEBT;
        }
        addDebt(creditorId, debtorId, amount);
        return SettlementStatus.SETTLED;
    }

    public List<Debt> balances() {
        List<Debt> result = new ArrayList<>();
        for (Map.Entry<PairKey, Long> entry : signedByPair.entrySet()) {
            PairKey key = entry.getKey();
            long signed = entry.getValue();
            if (signed > 0) {
                result.add(new Debt(key.first(), key.second(), Money.ofCents(signed)));
            } else {
                result.add(new Debt(key.second(), key.first(), Money.ofCents(-signed)));
            }
        }
        result.sort(Comparator.comparing(Debt::debtorId)
                .thenComparing(Debt::creditorId));
        return List.copyOf(result);
    }
}`}
</JavaFile>

### Calculate a non-mutating simplified view

The simplifier receives only Debt snapshots. Its priority-queue entries are immutable; after a match, it inserts a new entry for any remaining amount.

<JavaFile name="DebtSimplifier.java" purpose="Preserves every user's net position while suggesting at most U - 1 payments.">
{`import java.util.ArrayList;
import java.util.Comparator;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.PriorityQueue;

public final class DebtSimplifier {
    private record Account(String userId, long cents) {}

    public List<Debt> simplify(List<Debt> balances) {
        Map<String, Long> net = new HashMap<>();
        for (Debt debt : balances) {
            net.merge(debt.debtorId(), -debt.amount().cents(), Long::sum);
            net.merge(debt.creditorId(), debt.amount().cents(), Long::sum);
        }

        Comparator<Account> largestFirst = Comparator
                .comparingLong(Account::cents).reversed()
                .thenComparing(Account::userId);
        PriorityQueue<Account> debtors = new PriorityQueue<>(largestFirst);
        PriorityQueue<Account> creditors = new PriorityQueue<>(largestFirst);
        for (Map.Entry<String, Long> entry : net.entrySet()) {
            if (entry.getValue() < 0) {
                debtors.add(new Account(entry.getKey(), -entry.getValue()));
            } else if (entry.getValue() > 0) {
                creditors.add(new Account(entry.getKey(), entry.getValue()));
            }
        }

        List<Debt> suggestions = new ArrayList<>();
        while (!debtors.isEmpty() && !creditors.isEmpty()) {
            Account debtor = debtors.remove();
            Account creditor = creditors.remove();
            long transfer = Math.min(debtor.cents(), creditor.cents());
            suggestions.add(new Debt(
                    debtor.userId(),
                    creditor.userId(),
                    Money.ofCents(transfer)
            ));
            if (debtor.cents() > transfer) {
                debtors.add(new Account(debtor.userId(), debtor.cents() - transfer));
            }
            if (creditor.cents() > transfer) {
                creditors.add(new Account(creditor.userId(), creditor.cents() - transfer));
            }
        }
        return List.copyOf(suggestions);
    }
}`}

{`import java.util.ArrayList;
import java.util.EnumMap;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Set;

public final class ExpenseService {
    private final Map<String, User> usersById = new LinkedHashMap<>();
    private final Map<SplitType, SplitStrategy> strategies = new EnumMap<>(SplitType.class);
    private final List<Expense> expenses = new ArrayList<>();
    private final BalanceSheet balanceSheet = new BalanceSheet();
    private final DebtSimplifier simplifier = new DebtSimplifier();
    private int nextExpenseNumber = 1;

    public ExpenseService(List<User> users) {
        if (users == null || users.isEmpty()) {
            throw new IllegalArgumentException("Users are required");
        }
        for (User user : users) {
            if (usersById.putIfAbsent(user.id(), user) != null) {
                throw new IllegalArgumentException("Duplicate user: " + user.id());
            }
        }
        strategies.put(SplitType.EQUAL, new EqualSplitStrategy());
        strategies.put(SplitType.EXACT, new ExactSplitStrategy());
        strategies.put(SplitType.PERCENTAGE, new PercentageSplitStrategy());
    }

    public RecordExpenseResult recordExpense(
            String description,
            String payerId,
            Money total,
            List<String> participantIds,
            SplitType splitType,
            Map<String, Long> values
    ) {
        if (description == null || description.isBlank()
                || total == null || total.cents() == 0
                || participantIds == null || participantIds.isEmpty()
                || splitType == null || values == null
                || Set.copyOf(participantIds).size() != participantIds.size()) {
            return RecordExpenseResult.rejected(ExpenseStatus.INVALID_INPUT);
        }
        if (!usersById.containsKey(payerId)
                || participantIds.stream().anyMatch(id -> !usersById.containsKey(id))) {
            return RecordExpenseResult.rejected(ExpenseStatus.UNKNOWN_USER);
        }

        Map<String, Money> shares;
        try {
            shares = strategies.get(splitType)
                    .calculate(total, List.copyOf(participantIds), Map.copyOf(values));
        } catch (IllegalArgumentException | ArithmeticException error) {
            return RecordExpenseResult.rejected(ExpenseStatus.INVALID_SPLIT);
        }

        Expense expense = new Expense(
                "E" + nextExpenseNumber,
                description,
                payerId,
                total,
                splitType,
                shares
        );
        nextExpenseNumber++;
        expenses.add(expense);
        for (Map.Entry<String, Money> share : shares.entrySet()) {
            if (!share.getKey().equals(payerId)) {
                balanceSheet.addDebt(share.getKey(), payerId, share.getValue());
            }
        }
        return RecordExpenseResult.accepted(expense);
    }

    public SettlementStatus settle(
            String debtorId,
            String creditorId,
            Money amount
    ) {
        return balanceSheet.settle(debtorId, creditorId, amount);
    }

    public List<Expense> expenses() {
        return List.copyOf(expenses);
    }

    public List<Debt> balances() {
        return balanceSheet.balances();
    }

    public List<Debt> simplifiedDebts() {
        return simplifier.simplify(balanceSheet.balances());
    }
}`}

<h2 id="extensions">5. Extensions (~5 minutes)</h2>

### “Now support several groups”

The changed requirement adds group identity and membership. Today ExpenseService owns one user registry and one BalanceSheet. Introduce `Group` with members, expenses, and its own BalanceSheet, then let a thin service find a Group by ID. Do not put group IDs into every method while still sharing one global ledger.

### “Allow users to edit or delete an expense”

The affected rule is how accepted shares change balances. ExpenseService currently only applies debt forward. Add a reversible ledger operation: remove the old Expense contribution, validate and calculate the replacement completely, then apply the new contribution as one unit. An audit entry is useful because financial history should explain the change.

### “Record expenses from simultaneous requests”

The current scope assumes sequential calls. With two threads, expense IDs, history, and pair balances can race. In one Java process, protect the complete mutation boundary—ID allocation, history append, and all BalanceSheet updates—with one lock first. A database deployment needs a transaction and constraints; an in-process lock cannot protect several servers.

### “Support several currencies”

Money must now include a `Currency`, and expenses must state whether balances stay separated per currency or use an exchange rate. Keep rate lookup and conversion outside SplitStrategy. Never add raw USD cents to EUR cents.

### “Find the minimum possible number of payments”

DebtSimplifier currently uses a deterministic greedy rule and promises preserved net positions, not a global minimum. The new requirement changes its algorithm only, so a `DebtSimplificationStrategy` interface becomes justified. Keep the greedy version for large groups and add an exact search only for small groups, with the higher time cost stated clearly.

### A strong spoken summary

> “I first clarified payer versus participants, the three split types, cent rounding, pairwise netting, and rejection behavior. Money stores integer cents. Split strategies calculate a complete, exact share map before any state changes. BalanceSheet owns one signed value per user pair, while DebtSimplifier is a read-only view that preserves each user's net position. The current version is one in-memory group with sequential calls; groups, currencies, editing, and concurrent persistence are extensions.”
