<h2 id="requirements">1. Requirements (~5 minutes)</h2>

The interview begins with a short prompt:

> “Design a parking lot.”

That sentence sounds concrete because we have all used a parking lot. But it leaves the rules undecided. Can a motorcycle use a compact spot? Are there several floors? Who chooses the spot? Do we calculate a fee? If we answer those questions silently, we may build a correct solution to the wrong problem.

Start by turning the physical story into actions the program must perform. Do not name classes yet.

Read the arrows from left to right. A **Vehicle** enters through `ParkingLot.park`. **ParkingLot** checks whether that plate already has an active ticket, then asks **SpotAssignmentStrategy** for a selection. The strategy reads the ordered **ParkingFloor** groups and their spots. The chosen **ParkingSpot** performs `occupy(vehicle)` because it owns the changing availability. Only after that succeeds does ParkingLot return a **ParkingTicket**. If no selection exists, it returns a rejection and no spot changes.

The flow teaches an important boundary: the strategy may *choose* a spot, but it does not *occupy* it or issue tickets. Selection policy and parking-session state are separate jobs.

### Understand the allocation algorithm

The practical problem is not merely finding an empty spot. It is finding the **first compatible** spot according to a rule both interviewer and code understand.

Consider a car entering this lot:

1. Floor 0 has `M-01` free and `L-01` free.
2. Floor 1 has `C-11` free.
3. `M-01` is rejected because a car cannot fit there.
4. `L-01` is compatible and is on floor 0.
5. `C-11` is a tighter fit, but floor 1 is farther away.
6. The strategy chooses `L-01` because floor number is the first comparison.

The implementation filters unusable spots, creates a `SpotSelection` containing the floor and spot, and sorts candidates by three keys:

```text
floor number → fit preference → spot ID
```

If there are `S` spots, filtering costs `O(S)` and sorting costs `O(S log S)`. The lesson uses sorting because the rule is easy to read in an interview. A large fixed lot could maintain ordered free-spot sets and make selection faster, but every occupation and release would then need to keep those indexes correct.

<Insight title="Deterministic means ties have a rule" tone="warning">
  “Choose any free spot” makes tests unpredictable. The final spot-ID comparison means two equally suitable spots always produce the same answer. This is not a performance trick; it is a clarity and correctness rule.
</Insight>

### Decide whether a pattern helps

<PatternDecision name="Strategy for spot assignment" useIt={true}>
  The exact behavior expected to vary is `select(floors, vehicle)`. `ParkingLot` depends on the `SpotAssignmentStrategy` interface, and the current implementation is `NearestAvailableSpotStrategy`. If another lot later prefers the cheapest floor or reserves large spots, that rule changes in one implementation while duplicate checks, occupation, ticket creation, and exit remain untouched.
</PatternDecision>

<PatternDecision name="Factory for vehicles and spots" useIt={false}>
  Construction is simple and visible: each value needs an ID or plate and an enum type. A factory would hide straightforward constructors without resolving a current rule. Introduce one only if creation later needs several steps or configuration.
</PatternDecision>

<PatternDecision name="Singleton for ParkingLot" useIt={false}>
  Tests may create several independent lots, and a company may operate several locations. A normal object models that naturally. Global singleton state would make isolation harder and is not required by “one parking lot” in the prompt.
</PatternDecision>

### Code concepts to understand

<ConceptDropdown title="How Strategy is used here" summary="ParkingLot controls the workflow; the strategy answers only one question: which spot should be tried?" defaultOpen={true}>

`ParkingLot.park` calls `strategy.select(floors, vehicle)`. The strategy returns `Optional.empty()` when no candidate exists, or a `SpotSelection` containing the chosen floor and spot.

The strategy does not occupy the spot, create the ticket, or update active sessions. Those steps remain in `ParkingLot`, so replacing the selection rule cannot accidentally replace the rest of the parking workflow.

</ConceptDropdown>

<ConceptDropdown title="Why SpotSelection contains both floor and spot" summary="Exit and ticket creation need the floor that owns the chosen spot.">

Returning only `ParkingSpot` would force `ParkingLot` to scan every floor again to discover where it came from. `SpotSelection` is an immutable pair that keeps the result of the search together. It has value equality because it is a Java record.

</ConceptDropdown>

<ConceptDropdown title="Validation order protects state" summary="Every expected rejection happens before a ticket or spot is changed.">

`park` checks duplicate plate, then asks for a selection, then occupies the selected spot, and only then creates ticket indexes. `leave` finds the active ticket before releasing anything. Therefore an unknown ticket and a full-lot rejection leave all existing sessions unchanged.

</ConceptDropdown>

<ConceptDropdown title="Why Optional is useful for a missing selection" summary="No suitable spot is an expected search result, not a broken program.">

`SpotAssignmentStrategy.select` returns `Optional<SpotSelection>`. The caller must handle “nothing found” explicitly. Exceptions are reserved for impossible internal states or invalid object construction.

</ConceptDropdown>

<ConceptDropdown title="What this code does not guarantee about concurrency" summary="The current scope processes one request at a time inside one in-memory model.">

Two entrances could both select the same free spot before either calls `occupy`. That is a race condition: the result depends on how the operations interleave. `occupy` prevents the second mutation inside one sequential call, but the complete select → occupy → ticket operation is not protected as one unit.

If concurrent entrances become a requirement, protect that critical section with a lock in one Java process and add a deterministic two-caller test. Across several application servers, use a shared transaction, unique database constraint, optimistic version, or another shared consistency mechanism. An in-process Java lock cannot protect another server.

</ConceptDropdown>

```java
public enum SpotType {
    MOTORCYCLE,
    COMPACT,
    LARGE;

    public boolean canFit(VehicleType vehicleType) {
        return switch (vehicleType) {
            case MOTORCYCLE -> true;
            case CAR -> this == COMPACT || this == LARGE;
        };
    }

    public int preferenceFor(VehicleType vehicleType) {
        if (!canFit(vehicleType)) return Integer.MAX_VALUE;
        return switch (this) {
            case MOTORCYCLE -> 0;
            case COMPACT -> vehicleType == VehicleType.CAR ? 0 : 1;
            case LARGE -> vehicleType == VehicleType.CAR ? 1 : 2;
        };
    }
}
```

```java
        if (status == ParkingStatus.PARKED && ticket == null) {
            throw new IllegalArgumentException("PARKED requires a ticket");

        if (status != ParkingStatus.PARKED && ticket != null) {
            throw new IllegalArgumentException("Rejected parking cannot have a ticket");

        if (status == ParkingStatus.PARKED) {
```

### State-owning objects

Read `ParkingSpot.occupy` before `ParkingFloor`. It shows the most important state rule: check compatibility and availability before storing the vehicle. `ParkingFloor` then provides a safe group and lookup without exposing a mutable list.

<JavaFile name="ParkingSpot.java" purpose="Owns compatibility and the current occupant of one spot">

```java
import java.util.Objects;
import java.util.Optional;

public final class ParkingSpot {
    private final String id;
    private final SpotType type;
    private Vehicle occupiedBy;

    public ParkingSpot(String id, SpotType type) {
        if (id == null || id.isBlank()) {
            throw new IllegalArgumentException("spot id is required");
        }
        this.id = id;
        this.type = Objects.requireNonNull(type);
    }

    public boolean canFit(Vehicle vehicle) {
        return vehicle != null && type.canFit(vehicle.type());
    }

    public boolean occupy(Vehicle vehicle) {
        if (occupiedBy != null || !canFit(vehicle)) return false;
        occupiedBy = vehicle;
        return true;
    }

    public boolean release() {
        if (occupiedBy == null) return false;
        occupiedBy = null;
        return true;
    }

    public boolean isAvailable() {
        return occupiedBy == null;
    }

    public String getId() {
        return id;
    }

    public SpotType getType() {
        return type;
    }

    public Optional<Vehicle> getVehicle() {
        return Optional.ofNullable(occupiedBy);
    }
}
```

</JavaFile>

<JavaFile name="ParkingFloor.java" purpose="Owns one numbered group of spots and safe spot lookup">

```java
import java.util.HashSet;
import java.util.List;
import java.util.Objects;
import java.util.Optional;
import java.util.Set;

public final class ParkingFloor {
    private final int number;
    private final List<ParkingSpot> spots;

    public ParkingFloor(int number, List<ParkingSpot> spots) {
        if (number < 0) {
            throw new IllegalArgumentException("floor number cannot be negative");
        }
        Objects.requireNonNull(spots);
        if (spots.isEmpty()) {
            throw new IllegalArgumentException("a floor needs at least one spot");
        }

        Set<String> ids = new HashSet<>();
        for (ParkingSpot spot : spots) {
            Objects.requireNonNull(spot);
            if (!ids.add(spot.getId())) {
                throw new IllegalArgumentException("duplicate spot id on floor: " + spot.getId());
            }
        }
        this.number = number;
        this.spots = List.copyOf(spots);
    }

    public Optional<ParkingSpot> findSpot(String spotId) {
        return spots.stream()
                .filter(spot -> spot.getId().equals(spotId))
                .findFirst();
    }

    public int availableSpotCount() {
        return (int) spots.stream().filter(ParkingSpot::isAvailable).count();
    }

    public int getNumber() {
        return number;
    }

    public List<ParkingSpot> getSpots() {
        return spots;
    }
}
```

</JavaFile>

### Assignment policy

The interface is intentionally small. The current strategy reads every spot, removes occupied or incompatible candidates, and applies the exact ordering agreed in Requirements. The final spot-ID comparison is the deterministic tie-breaker.

<JavaFile name="SpotAssignmentStrategy.java" purpose="Replaceable boundary for choosing one spot">

```java
import java.util.List;
import java.util.Optional;

public interface SpotAssignmentStrategy {
    Optional<SpotSelection> select(List<ParkingFloor> floors, Vehicle vehicle);
}
```

</JavaFile>

<JavaFile name="NearestAvailableSpotStrategy.java" purpose="Chooses by floor, smallest suitable type, then spot ID">

```java
import java.util.Comparator;
import java.util.List;
import java.util.Objects;
import java.util.Optional;

public final class NearestAvailableSpotStrategy implements SpotAssignmentStrategy {
    @Override
    public Optional<SpotSelection> select(List<ParkingFloor> floors, Vehicle vehicle) {
        Objects.requireNonNull(floors);
        Objects.requireNonNull(vehicle);

        Comparator<SpotSelection> nearestFirst = Comparator
                .comparingInt((SpotSelection selection) -> selection.floor().getNumber())
                .thenComparingInt(selection ->
                        selection.spot().getType().preferenceFor(vehicle.type()))
                .thenComparing(selection -> selection.spot().getId());

        return floors.stream()
                .flatMap(floor -> floor.getSpots().stream()
                        .filter(ParkingSpot::isAvailable)
                        .filter(spot -> spot.canFit(vehicle))
                        .map(spot -> new SpotSelection(floor, spot)))
                .min(nearestFirst);
    }
}
```

</JavaFile>

### Parking workflow and demo

Read `ParkingLot.park` from top to bottom. Its order mirrors the requirement discussion: reject duplicate, select, occupy, issue ticket, index the session. `leave` reverses only the state recorded by a known ticket. `ParkingLotDemo` exercises success and both important rejection paths.

<JavaFile name="ParkingLot.java" purpose="Coordinates entry, tickets, spot occupation, and exit">

```java
import java.util.HashMap;
import java.util.HashSet;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Set;

public final class ParkingLot {
    private final List<ParkingFloor> floors;
    private final SpotAssignmentStrategy strategy;
    private final Map<String, ParkingTicket> activeTicketsById = new LinkedHashMap<>();
    private final Map<String, String> activeTicketIdByPlate = new HashMap<>();
    private int nextTicketNumber = 1;

    public ParkingLot(List<ParkingFloor> floors, SpotAssignmentStrategy strategy) {
        Objects.requireNonNull(floors);
        if (floors.isEmpty()) {
            throw new IllegalArgumentException("parking lot needs at least one floor");
        }
        validateUniqueFloorAndSpotIds(floors);
        this.floors = List.copyOf(floors);
        this.strategy = Objects.requireNonNull(strategy);
    }

    public ParkingResult park(Vehicle vehicle) {
        Objects.requireNonNull(vehicle);
        if (activeTicketIdByPlate.containsKey(vehicle.licensePlate())) {
            return ParkingResult.rejected(ParkingStatus.ALREADY_PARKED);
        }

        SpotSelection selection = strategy.select(floors, vehicle).orElse(null);
        if (selection == null) {
            return ParkingResult.rejected(ParkingStatus.NO_COMPATIBLE_SPOT);
        }
        if (!selection.spot().occupy(vehicle)) {
            throw new IllegalStateException("strategy returned an unusable spot");
        }

        String ticketId = String.format("T%03d", nextTicketNumber++);
        ParkingTicket ticket = new ParkingTicket(
                ticketId,
                vehicle.licensePlate(),
                selection.floor().getNumber(),
                selection.spot().getId());
        activeTicketsById.put(ticketId, ticket);
        activeTicketIdByPlate.put(vehicle.licensePlate(), ticketId);
        return ParkingResult.parked(ticket);
    }

    public ExitStatus leave(String ticketId) {
        if (ticketId == null || ticketId.isBlank()) {
            return ExitStatus.TICKET_NOT_FOUND;
        }
        ParkingTicket ticket = activeTicketsById.get(ticketId);
        if (ticket == null) return ExitStatus.TICKET_NOT_FOUND;

        ParkingSpot spot = floors.stream()
                .filter(floor -> floor.getNumber() == ticket.floorNumber())
                .findFirst()
                .flatMap(floor -> floor.findSpot(ticket.spotId()))
                .orElseThrow(() -> new IllegalStateException("ticket points to a missing spot"));
        if (!spot.release()) {
            throw new IllegalStateException("ticket points to an empty spot");
        }

        activeTicketsById.remove(ticketId);
        activeTicketIdByPlate.remove(ticket.licensePlate());
        return ExitStatus.RELEASED;
    }

    public List<ParkingTicket> getActiveTickets() {
        return List.copyOf(activeTicketsById.values());
    }

    public List<ParkingFloor> getFloors() {
        return floors;
    }

    private static void validateUniqueFloorAndSpotIds(List<ParkingFloor> floors) {
        Set<Integer> floorNumbers = new HashSet<>();
        Set<String> spotIds = new HashSet<>();
        for (ParkingFloor floor : floors) {
            Objects.requireNonNull(floor);
            if (!floorNumbers.add(floor.getNumber())) {
                throw new IllegalArgumentException("duplicate floor: " + floor.getNumber());
            }
            for (ParkingSpot spot : floor.getSpots()) {
                if (!spotIds.add(spot.getId())) {
                    throw new IllegalArgumentException("duplicate spot id: " + spot.getId());
                }
            }
        }
    }
}
```

<h2 id="extensions">5. Extensions (~5 minutes)</h2>

### “Now support two entrances at the same time”

The changed requirement affects the select → occupy → create-ticket sequence owned by `ParkingLot`. Two threads must not both act on the same selection. In one Java process, protect that complete critical section with a lock and demonstrate two callers competing for one spot, where exactly one receives `PARKED`. A lock around only `ParkingSpot.occupy` prevents two occupants, but the losing request must retry selection if another compatible spot exists. Across servers, move the guarantee to shared transactional storage; a local lock is not enough.

### “Prefer reserved or electric-charging spots for eligible vehicles”

Compatibility currently belongs to `SpotType`, and ranking belongs to `SpotAssignmentStrategy`. Add the new vehicle eligibility and spot capability, then update or replace the strategy. Do not place charging rules inside ticket creation.

### “Calculate a fee at exit”

The ticket must now remember entry time, and exit needs an exit time. Add a `PricingStrategy` only when several pricing rules are required, such as hourly, weekend, or vehicle-based pricing. Use an injected clock in tests so fee examples remain deterministic.

### “Show available counts on entrance boards”

Each floor already owns its spots, so it can calculate counts by spot type. For a small in-memory lot, calculating on request is simplest. If reads become frequent, add maintained counters beside `occupy` and `release`, then test that rejected actions do not change them.

### “Let drivers reserve a spot before arrival”

A boolean occupied/free state is no longer enough. Introduce explicit spot states such as `AVAILABLE`, `RESERVED`, and `OCCUPIED`, plus a reservation ID and expiry rule. This is the point where a state-transition design becomes useful; do not add those states to the basic version.
