<LessonStep id="game-design-intro">
<h2 id="class-design">3. Class design (10–15 minutes)</h2>

<WalkthroughOnly>
The entity step told us *which* objects we need. Class design turns each object into a clear promise: the state it protects, the behavior it owns, and the small public API other objects may use.

Use the same path for every class:

1. Start with one responsibility from the requirements.
2. Add only the state needed to perform that responsibility.
3. Put behavior beside the state it reads or changes.
4. Expose a public method only when another object or caller needs it.
5. Check relationships and protect the rules that must never be bypassed.

State is information an object remembers. Behavior is a decision or change it can perform using that information. An invariant is a rule that must remain true—for example, a cell cannot contain two marks and turns cannot change after a rejected move.
</WalkthroughOnly>

<FocusOnly><ClassDesignIntroduction /></FocusOnly>
</LessonStep>

<LessonStep id="pattern-future">
### Design Player

<WalkthroughOnly>
The requirement says that two players have names and fixed, different marks. That creates two fields: `name` and `mark`. They form one meaningful identity and never change during a match.

<DerivationTable rows={[
  ["Remember the player's name", "Player state", "private final String name"],
  ["Keep one assigned mark", "Player state", "private final Mark mark"],
  ["Prevent incomplete identity", "Player behavior", "validate in constructor"],
  ["Let Game identify the player", "Player API", "getName(), getMark()"]
]} />

`Player` does not place marks or manage turns. Those responsibilities need Board or Game state. Keeping both fields `private final` makes Player immutable: after construction, its identity cannot be changed into something that contradicts the match.

This is also cohesion: all Player members contribute to one focused job—representing a participant's stable identity.
</WalkthroughOnly>

<FocusOnly><ClassDesignClassifier scenario="player" /></FocusOnly>
</LessonStep>

<LessonStep id="board-design">
### Design Board

<WalkthroughOnly>
Board owns the changing grid. Any rule that can be answered by looking only at coordinates and cells belongs here: checking bounds, placing a mark, finding a winning line, checking whether the grid is full, clearing it, and reading one position.

<DerivationTable rows={[
  ["Store a fixed 3 by 3 grid", "Board state", "private final Mark[][] cells"],
  ["Reject bad coordinates", "Board behavior", "isInside(row, col)"],
  ["Reject an occupied cell", "Board behavior", "place(row, col, mark)"],
  ["Detect a winner", "Board behavior", "hasWinningLine(mark)"],
  ["Detect a draw condition", "Board behavior", "isFull()"],
  ["Expose board state safely", "Board behavior", "getMark(row, col)"],
  ["Start again", "Board behavior", "clear()"]
]} />

Encapsulation means an object protects its state and controls how that state changes. Board keeps `cells` private and never returns the array. A caller can read one position, but only Board can validate and modify its grid.

Board does not store `currentPlayer`, `winner`, or `status`. Those values require knowledge about the complete match, not only the grid.
</WalkthroughOnly>

<FocusOnly><ClassDesignClassifier scenario="board" /></FocusOnly>
</LessonStep>

<LessonStep id="game-design">
### Derive Game state

<WalkthroughOnly>
Game owns the match workflow. Take the requirements one sentence at a time. “Players alternate” creates `currentPlayer`. “Moves stop after completion” creates `status`. “Expose the winner” creates `winner`. Game also composes one Board and keeps both participants.

<DerivationTable rows={[
  ["Use one board for the match", "Game state", "private final Board board"],
  ["Two players use X and O", "Game state", "Player playerX, playerO"],
  ["Players alternate turns", "Game state", "Player currentPlayer"],
  ["Expose the winner", "Game state", "Player winner"],
  ["Stop after completion", "Game state", "GameStatus status"]
]} />

Game does not duplicate `cells`. Single responsibility does not mean “one method”; it means one reason for the class to change. Board changes when grid rules change. Game changes when match-flow rules change.
</WalkthroughOnly>

<FocusOnly><ClassDesignClassifier scenario="game-state" /></FocusOnly>
</LessonStep>

<LessonStep id="game-design-two">
### Derive Game behavior and its public API

<WalkthroughOnly>
Start from the main caller action: “player X places a mark at row 1, column 2.” That becomes `Game.makeMove`. Game validates match status and turn order, delegates cell work to Board, then records a win, draw, or next turn.

`reset` is another confirmed command. Read methods expose the current player, status, winner, and individual board cells. Internal changes such as switching a player or setting status must not become public setters.

<DerivationTable rows={[
  ["Accept one complete move", "Game public API", "makeMove(player, row, col)"],
  ["Start the match again", "Game public API", "reset()"],
  ["Expose one board position", "Game public API", "getMark(row, col)"],
  ["Expose match state", "Game public API", "getCurrentPlayer(), getWinner(), getStatus()"],
  ["Continue after an accepted move", "Game internal behavior", "switch currentPlayer"],
  ["Record completion", "Game internal behavior", "update winner and status"]
]} />

Returning `Board` would leak a mutable object: a caller could invoke `place` or `clear` without Game checking turns and status. `Game.getMark(row, col)` delegates a safe read while `makeMove` remains the only mutation path into the active match.
</WalkthroughOnly>

<FocusOnly><ClassDesignClassifier scenario="game-api" /></FocusOnly>
</LessonStep>

<LessonStep id="board-design-two">
### Connect the classes and apply the principles

<WalkthroughOnly>
Game **has a** Board and **has two** Players. Player has one Mark, and Board stores Mark values. These are composition relationships: a larger object is built from smaller objects with focused jobs.

There is no inheritance because none of these statements are true: “Game is a Board,” “Player is a Game,” or “Board is a Player.” Composition expresses the real relationships without coupling unrelated responsibilities.

- **Single responsibility:** Player owns identity, Board owns grid rules, and Game owns match flow.
- **Encapsulation:** fields stay private and mutation passes through the object that protects the rule.
- **Composition:** Game coordinates Board and Player objects instead of inheriting from them.
- **Immutability:** Player's name and mark cannot change after construction.
- **Cohesion:** each class keeps related state and behavior together.
</WalkthroughOnly>

<LessonStep id="pattern-decisions">
### Decide whether a pattern helps

<WalkthroughOnly>
Before choosing a pattern, ask what rule has multiple versions **right now**. The answer is none: there is one fixed board, one winning rule, and two human players. Direct composition is easier to explain and test.

<PatternDecision name="Strategy for the basic game" useIt={false}>
  The requirements contain one fixed winning rule and two human players. A `WinningStrategy` or `MoveStrategy` interface would create extra code without any second implementation. Write the direct rule first.
</PatternDecision>

<PatternDecision name="Singleton for Game" useIt={false}>
  We may want several games in tests or in a future tournament. A normal object supports that naturally. Global singleton state would make this harder.
</PatternDecision>

<PatternDecision name="Factory and Observer" useIt={false}>
  Constructors are enough for one simple setup, and the confirmed scope has no UI subscribers. Add factories or observers only when creation paths or notifications actually vary.
</PatternDecision>

<PatternDecision name="Strategy when several computer players are added" useIt={true}>
  If an extension requires easy, medium, and hard computer players, those are several ways to choose a move. At that point a `MoveStrategy` interface has a real purpose. Do not add it before that requirement arrives.
</PatternDecision>
</WalkthroughOnly>

<ConceptDropdown title="Validate first, change state second" summary="A rejected move must leave the board and current player exactly as they were." defaultOpen={true}>

`Game.makeMove` checks completion and turn order first. `Board.place` then checks the coordinates and cell. Only after placement succeeds does `Game` calculate the result or switch players.

This order is important. If the turn changed before the board accepted the move, clicking an occupied cell would incorrectly give the other player a turn.

<LessonStep id="ownership-concept">
<ConceptDropdown title="Board rules versus game workflow" summary="Board answers questions about cells; Game controls the match.">

`Board` knows whether a coordinate is valid, whether a cell is empty, whether a mark has a winning line, and whether the board is full. It does not know player names or whose turn it is.

`Game` knows the current player, status, and winner. It calls Board instead of reading or changing the cell array directly. This gives both classes one clear reason to change.

</ConceptDropdown>
</LessonStep>

<LessonStep id="enum-concept">
<ConceptDropdown title="Enums instead of strings and booleans" summary="Mark, GameStatus, and MoveResult give every meaningful state a clear name.">

An enum prevents invalid values such as `"FINSHED"` and avoids combinations of booleans such as `isWon=true` and `isDraw=true`. `MoveResult` also tells the caller why a move failed without throwing an exception for an expected user action.

</ConceptDropdown>
</LessonStep>

A pattern should solve a current source of change. The basic requirements do not include bots, several board sizes, or selectable winning rules, so extra interfaces would make the first design harder to read.

If the interviewer adds computer players, introduce `MoveStrategy`. If they add different winning rules, introduce `WinningRule`. The extension creates the need for the pattern.

</ConceptDropdown>

<LessonStep id="player-code">
### Player and board

`Player` is stable identity data: a name and one fixed mark. `Board` owns the mutable cell array and all rules that can be answered by looking only at that array. Notice that callers cannot receive and modify the array directly.

<WalkthroughOnly>
<JavaFile name="Player.java" purpose="A player's identity and fixed mark">

```java
import java.util.Objects;

public final class Player {
    private final String name;
    private final Mark mark;

    public Player(String name, Mark mark) {
        if (name == null || name.isBlank()) {
            throw new IllegalArgumentException("name is required");
        }
        this.name = name;
        this.mark = Objects.requireNonNull(mark);
    }

    public String getName() {
        return name;
    }

    public Mark getMark() {
        return mark;
    }

    @Override
    public String toString() {
        return name + " (" + mark + ")";
    }
```

```java
import java.util.Arrays;

public final class Board {
    public static final int SIZE = 3;
    private final Mark[][] cells = new Mark[SIZE][SIZE];

    public boolean place(int row, int column, Mark mark) {
        if (!isInside(row, column) || mark == null) return false;
        if (cells[row][column] != null) return false;
        cells[row][column] = mark;
        return true;
    }

    public boolean isInside(int row, int column) {
        return row >= 0 && row < SIZE && column >= 0 && column < SIZE;
    }

    public boolean hasWinningLine(Mark mark) {
        for (int index = 0; index < SIZE; index++) {
            if (cells[index][0] == mark
                    && cells[index][1] == mark
                    && cells[index][2] == mark) {
                return true;
            }
            if (cells[0][index] == mark
                    && cells[1][index] == mark
                    && cells[2][index] == mark) {
                return true;
            }
        }

        boolean mainDiagonal = cells[0][0] == mark
                && cells[1][1] == mark
                && cells[2][2] == mark;
        boolean otherDiagonal = cells[0][2] == mark
                && cells[1][1] == mark
                && cells[2][0] == mark;

        return mainDiagonal || otherDiagonal;
    }

    public boolean isFull() {
        for (Mark[] row : cells) {
            for (Mark cell : row) {
                if (cell == null) return false;
            }
        }
        return true;
    }

    public Mark getMark(int row, int column) {
        if (!isInside(row, column)) {
            throw new IndexOutOfBoundsException("Cell is outside the board");
        }
        return cells[row][column];
    }

    public void clear() {
        for (Mark[] row : cells) {
            Arrays.fill(row, null);
        }
    }

    @Override
    public String toString() {
        StringBuilder output = new StringBuilder();
        for (int row = 0; row < SIZE; row++) {
            for (int column = 0; column < SIZE; column++) {
                Mark mark = cells[row][column];
                output.append(mark == null ? "." : mark);
                if (column < SIZE - 1) output.append(" ");
            }
            output.append(System.lineSeparator());
        }
        return output.toString();
    }
}
```

<LessonStep id="game-overview">
### Game controller

`Game.makeMove` is the central workflow and should be read from top to bottom: reject illegal game state, reject the wrong player, validate the cell, place the mark, calculate the result, and switch the turn only if play continues. `TicTacToeDemo` proves how the public API is meant to be used.

<PredictReveal prompt="Where is the safest place to switch currentPlayer?">
  Only in the final `else`, after the move was accepted and after the code confirmed that the game did not end. A rejected, winning, or drawing move must not switch the turn.
</PredictReveal>

<WalkthroughOnly>
<JavaFile name="Game.java" purpose="Controls turns, status, and the move workflow">

```java
import java.util.Objects;

public final class Game {
    private final Board board;
    private final Player playerX;
    private final Player playerO;
    private Player currentPlayer;
    private Player winner;
    private GameStatus status;

    public Game(Player first, Player second) {
        Objects.requireNonNull(first);
        Objects.requireNonNull(second);
        if (first.getMark() == second.getMark()) {
            throw new IllegalArgumentException("Players need different marks");
        }

        this.playerX = first.getMark() == Mark.X ? first : second;
        this.playerO = first.getMark() == Mark.O ? first : second;
        this.board = new Board();
        reset();
    }

    public MoveResult makeMove(Player player, int row, int column) {
        if (status != GameStatus.IN_PROGRESS) {
            return MoveResult.GAME_ALREADY_OVER;
        }
        if (player != currentPlayer) {
            return MoveResult.NOT_YOUR_TURN;
        }
        if (!board.isInside(row, column)) {
            return MoveResult.OUT_OF_BOUNDS;
        }
        if (!board.place(row, column, player.getMark())) {
            return MoveResult.CELL_OCCUPIED;
        }

        if (board.hasWinningLine(player.getMark())) {
            winner = player;
            status = player.getMark() == Mark.X
                    ? GameStatus.X_WON
                    : GameStatus.O_WON;
        } else if (board.isFull()) {
            status = GameStatus.DRAW;
        } else {
            currentPlayer = currentPlayer == playerX ? playerO : playerX;
        }

        return MoveResult.ACCEPTED;
    }

    public void reset() {
        board.clear();
        currentPlayer = playerX;
        winner = null;
        status = GameStatus.IN_PROGRESS;
    }

    public Mark getMark(int row, int column) {
        return board.getMark(row, column);
    }

    public Player getCurrentPlayer() {
        return currentPlayer;
    }

    public Player getWinner() {
        return winner;
    }

    public GameStatus getStatus() {
        return status;
    }
}
```

```java
public final class TicTacToeDemo {
    public static void main(String[] args) {
        Player alice = new Player("Alice", Mark.X);
        Player bob = new Player("Bob", Mark.O);
        Game game = new Game(alice, bob);

        play(game, alice, 0, 0);
        play(game, bob,   1, 0);
        play(game, alice, 0, 1);
        play(game, bob,   1, 1);
        play(game, alice, 0, 2);

        printBoard(game);
        System.out.println("Status: " + game.getStatus());
        System.out.println("Winner: " + game.getWinner());
    }

    private static void play(Game game, Player player, int row, int column) {
        MoveResult result = game.makeMove(player, row, column);
        System.out.printf("%s -> (%d,%d): %s%n",
                player.getName(), row, column, result);
    }

    private static void printBoard(Game game) {
        for (int row = 0; row < Board.SIZE; row++) {
            for (int column = 0; column < Board.SIZE; column++) {
                Mark mark = game.getMark(row, column);
                System.out.print((mark == null ? "." : mark)
                        + (column == Board.SIZE - 1 ? "" : " "));
            }
            System.out.println();
        }
    }
}
```

<LessonStep id="extension-strategies">
<h2 id="extensions">5. Extensions (~5 minutes)</h2>

### “Add computer players with several difficulty levels”

Now introduce a `MoveStrategy` interface with `chooseMove(Board)`. Easy, medium, and hard bots implement different selection rules. Human players still receive moves from input, so do not put minimax logic inside `Board` or `Game`.
</LessonStep>

<LessonStep id="extension-board">
### “Support an N by N board and K marks in a row”

Pass size into `Board` and move win checking behind a `WinningRule` interface. The fixed eight-line implementation can then be replaced without changing the turn workflow in `Game`.
</LessonStep>

<LessonStep id="extension-state">
### “Add undo”

Store each accepted move in a stack. `undo()` removes the most recent mark, restores the previous player, and changes status back to `IN_PROGRESS`. Rejected moves never enter the history.

### “Play over a network”

Keep this domain model. Add a service around `Game` that identifies the remote player, serializes commands, and ensures that two moves cannot update one game at the same time.
</LessonStep>
