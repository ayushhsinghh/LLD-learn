<section id="class-design">

## 3. Class design

Use the chain **requirement → responsible object → state → behavior → public API → relationships → principles → patterns**. Begin at `NotificationService.submit`, then follow its dependencies downward.

### Design the immutable request and result values

Once a request is queued, a worker must see the same recipient, channel, and content that the caller submitted. `NotificationRequest` therefore validates its required values during construction and exposes no setters. `SubmissionReceipt` returns the new job ID, while `DeliverySnapshot` publishes a consistent read of mutable progress.

<DerivationTable rows={[
  ["Keep one accepted message stable", "NotificationRequest value", "recipientId, destination, channel, subject, body"],
  ["Reject incomplete content before queueing", "NotificationRequest behavior", "constructor validation"],
  ["Return immediately after acceptance", "SubmissionReceipt value", "jobId"],
  ["Expose progress without exposing the job", "DeliverySnapshot value", "status, attempts, lastError"]
]} />

### Design channel senders and RetryPolicy

EMAIL, SMS, and PUSH are three implementations of the same operation. `NotificationSender` is a small Strategy interface with `channel()` and `send(request)`. The service uses a channel-to-sender registry, so adding a sender does not add another branch to the delivery workflow.

`RetryPolicy` is an immutable value with one rule: after a completed attempt, decide whether another is permitted. A maximum of three means one initial attempt and two retries; it does not mean three retries after the first failure.

<DerivationTable rows={[
  ["Keep provider code outside the workflow", "NotificationSender API", "channel() and send(request)"],
  ["Support one implementation per channel", "Sender strategies", "EmailSender, SmsSender, PushSender"],
  ["Stop after three total attempts", "RetryPolicy", "maxAttempts and canRetry(completedAttempts)"],
  ["Keep delay rules out of the first version", "RetryPolicy boundary", "no sleep, backoff, or scheduling state"]
]} />

### Design DeliveryJob

`DeliveryJob` is the private mutable state owner. Its job ID and request never change; status, attempt count, and last error move together. Synchronized transition and snapshot methods prevent a querying caller from observing a new status with an old attempt count.

<DerivationTable rows={[
  ["Remember immutable work identity", "DeliveryJob state", "jobId and NotificationRequest"],
  ["Expose current progress", "DeliveryJob state", "status, attempts, lastError"],
  ["Begin and complete one attempt", "DeliveryJob internal behavior", "markSending, markSent, recordFailure"],
  ["Never restart terminal work", "DeliveryJob invariant", "SENT and FAILED reject further transitions"],
  ["Publish a safe read", "DeliveryJob API", "snapshot() returns DeliverySnapshot"]
]} />

### Derive NotificationService state and API

The service coordinates submission and execution. Its public API is deliberately small: `submit`, `getStatus`, and `close`. Sender lookup, worker creation, the retry loop, and job transitions stay internal. Callers never receive a mutable DeliveryJob, sender registry, executor queue, or public status setter.

<DerivationTable rows={[
  ["Route without channel branches", "NotificationService state", "Map<NotificationChannel, NotificationSender> senders"],
  ["Find accepted jobs by ID", "NotificationService state", "ConcurrentHashMap jobs"],
  ["Run several jobs without blocking submit", "NotificationService state", "ExecutorService executor"],
  ["Create unique job IDs safely", "NotificationService state", "AtomicLong sequence"],
  ["Accept and inspect work", "NotificationService API", "submit(request) and getStatus(jobId)"],
  ["Stop new work and drain accepted tasks", "NotificationService API", "close()"]
]} />

### The asynchronous correctness boundary

A method call such as `sender.send()` is synchronous inside one worker: that worker waits for the provider attempt. The **public workflow** is asynchronous because `submit()` schedules the worker and returns first. This distinction prevents a common interview mistake—calling a method “async” merely because a thread pool exists while still waiting for its result.

The service must index the job before scheduling it. Otherwise a fast worker could finish before `jobs.put`, producing a moment where the caller has an ID but status lookup cannot find the completed work. If the executor rejects scheduling, remove the indexed job and fail submission; do not leave unreachable QUEUED work.

Each accepted job has one worker task, so two workers never intentionally deliver the same job in this model. Status readers still run concurrently with that worker. Synchronized job methods make each multi-field transition and snapshot visible as one consistent state.

<PatternDecision name="Strategy" useIt={true}>The confirmed requirement has three versions of one delivery operation. NotificationSender isolates this variation and lets the service registry select it.</PatternDecision>
<PatternDecision name="Factory" useIt={false}>The application can construct and inject the three senders directly. There is no complex creation rule.</PatternDecision>
<PatternDecision name="Singleton" useIt={false}>Global access does not improve correctness, durability, or testing. Explicit construction makes executor ownership clear.</PatternDecision>
<PatternDecision name="Observer or Chain of Responsibility" useIt={false}>There are no delivery subscribers or channel fallback chain in the confirmed requirements.</PatternDecision>

### Connect the classes and review the final blueprint

NotificationService composes the sender registry, RetryPolicy, ExecutorService, and private DeliveryJobs. A worker delegates one attempt to a NotificationSender and reports the outcome back through DeliveryJob transitions. No inheritance is needed between the service, job, policy, or infrastructure.

- **Immutability:** queued content and returned snapshots remain stable.
- **Encapsulation and thread safety:** only DeliveryJob transition methods may change live status.
- **Single responsibility:** the service coordinates while each sender owns provider-specific delivery.
- **Open/closed and dependency inversion:** the workflow depends on NotificationSender rather than channel implementations.
- **Composition:** executor and retry policy are explicit collaborators with visible ownership and lifecycle boundaries.

<JavaFile name="NotificationService.java" code={`import java.util.EnumMap;
import java.util.List;
import java.util.Map;
import java.util.Objects;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.RejectedExecutionException;
import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.atomic.AtomicLong;

public final class NotificationService implements AutoCloseable {
    private final Map<NotificationChannel, NotificationSender> senders;
    private final ConcurrentMap<String, DeliveryJob> jobs = new ConcurrentHashMap<>();
    private final ExecutorService executor;
    private final RetryPolicy retryPolicy;
    private final AtomicLong sequence = new AtomicLong(1);
    private final AtomicBoolean accepting = new AtomicBoolean(true);

    public NotificationService(List<NotificationSender> senders,
            ExecutorService executor, RetryPolicy retryPolicy) {
        this.executor = Objects.requireNonNull(executor);
        this.retryPolicy = Objects.requireNonNull(retryPolicy);
        EnumMap<NotificationChannel, NotificationSender> registry =
                new EnumMap<>(NotificationChannel.class);
        for (NotificationSender sender : List.copyOf(senders)) {
            if (registry.putIfAbsent(sender.channel(), sender) != null) {
                throw new IllegalArgumentException("Duplicate sender: " + sender.channel());
            }
        }
        this.senders = Map.copyOf(registry);
    }

    public SubmissionReceipt submit(NotificationRequest request) {
        Objects.requireNonNull(request);
        if (!accepting.get()) {
            throw new IllegalStateException("Service is closed");
        }
        if (!senders.containsKey(request.channel())) {
            throw new IllegalArgumentException("No sender for " + request.channel());
        }
        String jobId = "N" + String.format("%03d", sequence.getAndIncrement());
        DeliveryJob job = new DeliveryJob(jobId, request);
        jobs.put(jobId, job);
        try {
            executor.submit(() -> deliver(job));
        } catch (RejectedExecutionException failure) {
            jobs.remove(jobId);
            throw failure;
        }
        return new SubmissionReceipt(jobId);
    }

    private void deliver(DeliveryJob job) {
        NotificationSender sender = senders.get(job.request().channel());
        while (true) {
            job.startAttempt();
            try {
                sender.send(job.request());
                job.markSent();
                return;
            } catch (DeliveryException failure) {
                String message = failure.getMessage() == null
                        ? "Delivery failed"
                        : failure.getMessage();
                job.recordAttemptFailure(message);
                if (!retryPolicy.canRetry(job.attempts())) {
                    job.markFailed();
                    return;
                }
            }
        }
    }

    public Optional<DeliverySnapshot> getStatus(String jobId) {
        if (jobId == null || jobId.isBlank()) {
            return Optional.empty();
        }
        DeliveryJob job = jobs.get(jobId);
        return job == null ? Optional.empty() : Optional.of(job.snapshot());
    }

    @Override
    public void close() {
        if (accepting.compareAndSet(true, false)) {
            executor.shutdown();
        }
    }
}`} />

## 5. Extensions

### Durable delivery across crashes

The changed requirement is “accepted jobs must survive a process crash.” `NotificationService` currently owns an in-memory executor and job index, so those can no longer be the authority. Persist an outbox record in the same transaction as the caller's business action or publish to a durable broker. Workers acknowledge only after delivery handling, failed jobs move to a dead-letter destination, and stable delivery keys reduce duplicate effects.

### Backoff, jitter, and rate limits

The current `RetryPolicy` decides only whether another immediate attempt is allowed. A delayed retry requirement introduces scheduled time. Replace the immediate loop with a retry scheduler that calculates the next attempt time. Add jitter so many jobs do not retry together, and keep provider-specific rate limits beside the sender or its adapter.

### New channels, templates, and fallback

WhatsApp or Slack adds a channel value and `NotificationSender`; the service workflow remains unchanged. Templates introduce a renderer before submission so the accepted request still contains final immutable content. Channel fallback is different: it turns one request into an ordered multi-channel plan and may justify a Chain of Responsibility only after the fallback requirement is precise.

<Insight title="A strong closing explanation">“I separated acceptance from delivery: submit validates and indexes a QUEUED job before handing one task to a fixed executor. NotificationSender is the Strategy boundary for EMAIL, SMS, and PUSH. DeliveryJob synchronizes its lifecycle and exposes immutable snapshots. NotificationService owns routing and three immediate attempts, but I would move accepted work to durable shared infrastructure before claiming crash recovery or cross-server guarantees.”</Insight>
